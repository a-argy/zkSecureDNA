# zkSecureDNA proof design (v2: SP1 6, bound statement)

This document pins down exactly what the final proof claims, what each circuit
contributes, and what is still trusted. It replaces the v1 prototype design
(SP1 3.0, unbound sub-proofs).

## What was wrong with v1

v1 had three circuits (hash, checksum, aggregation) that each ran correctly,
but nothing tied them to each other or to the order being screened:

1. **Sub-proof keys came from the prover.** The aggregation circuit read the
   hash/checksum verifying keys from its input, so any valid SP1 proof of any
   program would pass.
2. **Sub-proof outputs were never compared to the query state.** The
   aggregation circuit received the full query state as a separate private
   input and never checked it against what the hash proof committed.
3. **The checksum input was supplied, not computed.** The checksum circuit
   read the hash of the queries as an input rather than deriving it.
4. **The HDB trusted the client's verifying key** and never compared the
   proof's public values to the hashes it was asked to screen, so an old proof
   could accompany a new order. A bad proof panicked the request handler.
5. **The active-security random modifier became public.** v1 derived it from
   the queries (which keyservers see), where upstream draws it fresh and keeps
   it from keyservers. v2 restores a fresh secret modifier and binds it with a
   commitment instead.

## The v2 statement

The final (aggregation) proof publicly commits a single `ScreeningStatement`:

| Field | Meaning |
|---|---|
| `order_commitment` | `SHA-256(salt ‖ windows)`: a hiding commitment to the exact DNA windows screened. The lab keeps `salt` and can later open it to an authorized party. |
| `queries_digest` | `SHA-256` of every blinded query sent to keyservers, checksum query included. |
| `responses_digest` | `SHA-256` of every keyserver response (id + parts), in order. |
| `keyserver_ids` | Which keyservers answered. |
| `active_security_key_digest` | `SHA-256` of the public active-security commitments used. |
| `hdb_hashes_digest` | `SHA-256` of the final hashes sent to the HDB. |

Read as a sentence: *"For some DNA windows matching `order_commitment`, the
blinded queries in `queries_digest` were derived correctly; the keyserver
responses in `responses_digest` passed the active-security check against the
published key; and the hashes sent to the HDB are the correct DOPRF outputs
for those windows."*

## Circuits

**hash** (private: windows, blinding factors, salt) commits
`order_commitment` and `digest(queries)` for the per-window queries.

**checksum** (private: the weighted sum of window points, fresh random
modifier `r`, checksum verification factor and blinding factor; public input:
active-security key) recomputes the checksum query and commits
`digest(checksum query)`, `SHA-256(r)` and the active-security key digest.
The weighted sum need not be bound here: if it is wrong, honest keyserver
responses fail the active-security check inside the aggregation circuit, so a
wrong sum can only make the lab's own proof fail.

**aggregate** verifies both sub-proofs against verifying-key digests
**compiled into the guest** (generated by `zk/xtask`), then checks:

- the query state's per-window queries hash to the hash proof's digest,
- its checksum query and `r` match the checksum proof's commitments,
- the keyserver responses pass active-security validation,

and commits the `ScreeningStatement`.

## HDB endpoint

`/scep/screen-and-verify` now:

1. verifies the proof against the aggregation verifying key **pinned at
   startup** from the HDB's own copy of the ELF, ignoring any client-supplied key;
2. decodes the `ScreeningStatement` and requires `hdb_hashes_digest` to equal
   the digest of the hashes in the request, and the active-security digest to
   equal the deployment's key;
3. returns a typed error, not a panic, on any failure.

## Still trusted (addressed in step 3)

- **Keyserver responses are unsigned.** A lab can invent its own key, play
  every keyserver itself, and produce a valid proof. The fix is signed
  responses plus a per-keyserver DLEQ (Chaum–Pedersen) proof that
  `response = query^{keyshare·λ}` against the keyserver's published
  `g^{keyshare}`, verified inside the aggregation circuit.
- **The HDB's answer is unsigned.** The HDB should sign
  `(hdb_hashes_digest, result)` so the lab can show a third party what it was told.

## Proof modes

`ZK_PROOF_MODE` = `execute` (run the circuits, no proof; for development),
`prove` (real compressed proofs), or `off` (upstream behaviour).
